# Incott 鼠标 HID 协议（逆向整理）

> 来源：从 Incott 网页驱动（`incott.net/mouse`，GitHub 离线镜像 `oexi/incott-driver-offline`）的
> 混淆 JS 中反混淆还原。所有命令为 8 字节 Feature Report，report ID = 9。

## 1. 设备识别

| 项 | 值 |
|---|---|
| VID | `0x093A`（PixArt 原相） |
| PID 有线 | `0x622C`（25132） |
| PID 无线 | `0x522C`（21036） |
| usagePage | `0xFF05`（vendor-defined） |
| usage | `0x0001` |

> **Col02 接口**：插线充电时 `0xFF05` 会同时出现 Col01/Col02 两个接口（usage 均为 `0x0001`）。
> Col01 发送 Feature Report 会失败（`HidD_SetFeature` 报错），必须用 Col02（枚举靠后的那个）通信。
> 无线时通常只有一个接口。见 `src/main/hid.js` 的 `openDevice`（逐个尝试、Col02 优先）。

传感器（由 `0x8F` 型号信息读取，有线取 buf[4] / 无线取 buf[5]）：
- 字节值 `240`（或未知）= PAW3395（最大 32000 DPI）
- 字节值 `241` = PAW3950（最大 45000 DPI，14672 十进制）
- 内部表示沿用 `0x3395` / `0x3950`（见 `protocol.js SENSOR` / `parseModelInfo`）

无线判定：`productId === 0x522C`。

## 2. 通信机制

- 所有配置通过 **HID Feature Report** 收发，**report ID = 9**。
- 发送：`sendFeatureReport(9, data)`，`data` 为 8 字节 `[cmd, p1..p7]`。
- 接收：`receiveFeatureReport(9)`，返回数据区（含命令码回显）。
- 即时命令（宏分块上传等）另走 `sendReport(9, data)`（Output Report）。

WebHID → node-hid 适配：
| WebHID | node-hid |
|---|---|
| `sendFeatureReport(9, data)` | `device.sendFeatureReport([9, ...data])` |
| `receiveFeatureReport(9)` | `device.getFeatureReport(9, LEN)`（LEN 待实机确认，暂定 8） |
| `sendReport(9, data)` | `device.write([9, ...data])` |

## 3. 命令表（byte 0 = 命令码）

### 3.1 轮询率 `[1, val, 0,0,0,0,0,0]`
`val` → 频率：`0=1000, 1=500, 2=250, 3=125, 4=8000, 5=4000, 6=2000`（Hz）

> **硬件钳制（实机验证）**：有线 / 非 8K 接收器上请求 2000/4000/8000Hz 会被固件钳制为 1000Hz
> （写后回读 0x81 证实）。应用层在写入前按 0x8F 读到的接收器类型预钳制（`protocol.js clampRate`）。

### 3.2 DPI 档位值 `[2, ix, dL, dH, 0,0,0, flag]`
- `ix`：档位索引
- `dL/dH`：DPI **硬件值**（16 位小端），硬件值 = `(实际DPI - 50) / 50`
- `flag`：`0`=单档；XY 分离时 `1`=X 轴第一段、`2`=Y 轴第二段（需分两次发送，中间 sleep 100ms）

> **注意**：早前（2026-11-14）曾判定"G24 不支持 XY 独立"（axis=0/1/2 读取均返回同一值）；
> **2026-11-16 用户实机复核推翻了这条**：按 `flag=1/2` 分别写 X、Y 后切档，两轴的实际移速确实不同。
> 所以"axis 读回同值"只能说明该读命令不吃 axis 参数，不代表硬件不支持独立写入。
> XY 分离按**已支持**处理，仍以 `flag=1/2` 分两包下发（间隔 ≥100ms）。

### 3.3 DPI 档位切换 `[3, levels, curDpi, 0,0,0,0,0]`
- `levels`：档位总数
- `curDpi`：当前档位索引

### 3.4 传感器高级 `[4, sub, val, 0,0,0,0,0]`
| sub | 含义 | val |
|---|---|---|
| 1 | LOD 抬升距离 | `0=0.7mm, 1=1mm, 2=2mm`；**PAW3950 需旋转映射**：UI 0→hw 2, UI 1→hw 0, UI 2→hw 1（官方 apply 流程原样行为，见 `protocol.js lodToHw`） |
| 2 | Ripple 波纹 | 0/1 |
| 3 | Angle Snap 角度吸附 | 0/1 |
| 4 | Motion Sync 运动同步 | 0/1 |
| 5 | Sensor Mode | 见 3.8 |

### 3.5 杂项 `[5, sub, ...]`
| sub | 含义 | 参数 |
|---|---|---|
| 1 | 去抖时间 Debounce | `[5,1,t]`，t ≤ 30 |
| 2 | 火力键参数 | `[5,2,lp,t]`，lp=循环次数(≤3)，t=间隔 |
| 3 | 睡眠时间（官网叫「节能调节」） | `[5,3,tL,tH]`，16 位秒，官方档位 `10,20,30,60,120,180,240,300,360,420,480,540,600,660,720,780,840,900` |

> **节能调节**：官方文案是「节能调节(S)」（原生驱动 `str_PowerDownTime`）与
> 「鼠标静置后，到停止工作的时间」（网页驱动 msg70/71）。档位取自网页驱动 `DormancyTime`
> 数组，UI 用 ± 逐档切换而不是自由输入。回读 `0x85,3` 得到当前秒数（G24 实测 600s）。
> 见 `protocol.js` 的 `SLEEP_STEPS` / `nearestSleepStep`。

### 3.6 按键映射 `[6, index, k1,k2,k3,k4, 0,0]`
- `index`：按键矩阵位置（0=左键,1=右键,2=中键,3=后退,4=前进,5=DPI键）
- `k1..k4`：32 位键码（小端，k1 最低字节）

### 3.7 宏分块上传 `[7, ict, i, 32, bID, 0,0,0]`
- 宏数据 320 字节，分 10 块，每块 32 字节，用 Output Report（`sendReport`）上传
- `ict=10`（块数），`i`=当前块，`bID`=宏槽位

### 3.8 接收器 LED `[8, mode, 0,0,0,0,0,0]`（8K 接收器专用）

| mode | UI 名称（官方 msg64/65/66） | 行为（官方 msg75/76/77 原文） |
|---|---|---|
| 0 | 连接状态和回报率 | 只有当鼠标连接到接收器时，才会按照不同回报率对应的颜色点亮 |
| 1 | 电池状态 | 从绿色（100%）黄色（66%）橙色（33%）和红色（0%）逐渐变化 |
| 2 | 仅警告电池 | 始终保持熄灭，仅在鼠标需要充电时闪烁红灯 |

**回报率颜色映射（官方给定，不可自定义）**：
红色 125Hz / 蓝色 250Hz / 黄色 500Hz / 橙色 1000Hz / 紫色 2000Hz / 绿色 4000Hz / 白色 8000Hz。

回读用 `0x88`，值在 buf[1]。官方网页驱动只有这三个选项。
> 文案与颜色表均来自官方离线驱动 `_ref/incott-driver-offline/js/text_sc-v106.js`（msg63~66、msg75~77）。
> 注意官方 UI 排列顺序是「电池状态 | 连接状态和回报率 | 仅警告电池」，与协议值 0/1/2 顺序不同。

### 3.8b 本体 DPI 键指示灯：**不可设置**（实测结论，2026-11-14）

DPI 键上那颗指示灯与接收器 LED（命令 8）是两套灯。它在切 DPI 时/低电量时会亮红灯，属固件行为。

**验证过程与证据**：

1. 官方桌面驱动 v1.3.7（`F:\Software\incott-app(1.3.7)\GamingMouse.exe`）能识别 G24 并完整下发配置，
   抓到的真实序列（Feature Report ID 9，只读旁路捕获）：
   `8F…`（型号）→ `85 06 00 00 F1…`（网页驱动未实现的 sub 6，buf[4]=241 传感器 ID）→
   `82 01 83 03 … 01/02`（DPI，buf[7] 区分 X/Y）→ `83 02…` → `84 01..05` → `85 01/03/02` →
   `86 00..05`（键位）→ `88 01`（接收器 LED=电池状态）。
   **整段没有任何灯效命令**。
2. 该驱动 UI 里也没有「DPI灯效」入口（语言包 `Language/ch.xml` 虽有 `str_dpi_led_dx_text=DPI灯效`、
   `dx1=常亮/dx2=呼吸/dx3=关闭`，但 G24 不显示该项）。
3. 盲试 `[0x0A, v]`（v = 0/1/2/3~8 及若干复合包）**均无法点亮**该灯。早前 `[0x0A,2]` 之后“灯灭了”
   是误判——这颗灯本来就不是常亮状态，只在切 DPI 或低电量时亮。

**结论**：G24 固件不提供该灯的设置能力（至少这版固件 + 官方驱动组合下拿不到），
驱动与本工具都无法让它常亮。`0x0A` 不是它的命令，别再用。

> 附：原生驱动里那 6 个 `str_led_off/neon/breathing/flicker/flowwater/ambilight` 是**接收器模式名**
> （`off=关闭 / neon=仅警告电池 / breathing=电池状态 / flicker=连接状态和回报率`），与本灯无关。

> **鼠标本体灯效：硬件有灯，网页驱动没有实现。** 本体在 DPI 键处有一颗指示灯（用户实测会亮红灯）。
> 官方**原生**驱动 `GamingMouse.exe`（安装包内，PDB 路径 `D:\work\vs\GamingMouse-2862-IM2324`）
> 有完整的 LED 设置对话框 `CLedSetDlg`，字符串表含 6 种模式
> `str_led_off / neon / breathing / flicker / flowwater / ambilight`，另有 DPI 灯相关资源
> `str_dpi_led_dx_text / str_dpi_led_dx1 / dx2 / dx3`。
>
> 官方**网页**驱动把这部分砍掉了：设备层方法只有 `setReceiverLED`；DPI 弹窗里的颜色块 `#ff0866`
> 纯属展示（`<input type="color">` 被注释掉）；`.ict` 的 `dpicolor[]` 只存档不下发
> —— `setResolution(ix,d1,d2)` 组包为 `[2, ix, dL, dH, 0, 0, 0, flag]`，buf[4..6] 恒为 0，
> `flag` 仅区分 XY 同值(0)/X(1)/Y(2)（Y 值在 100ms 后的第二包里重发）。
> 所以本体灯的颜色/灯效当前完全由固件决定，网页驱动与本工具都改不了；
> 要支持需 USB 抓包或反汇编 `GamingMouse.exe` 拿到命令字。

> **彩色 DPI 灯色：能写能读，但 G24 固件不点灯（2026-11-15 A/B 实测）。**
> 把第 1 档写成纯绿 `00 FF 00`、第 2 档写成纯红 `FF 00 00`（DPI 值不变），`0x82` 回读完全一致、
> 断电重连仍在，但按 DPI 键切档时那颗指示灯颜色**一模一样**。
> 所以 `buf[4..6]` 只是被存进 flash 的字段，G24 固件不用它驱动 LED。
> 官方两版驱动也确实没有调色板：网页版颜色块是装饰，原生版只有「DPI灯效：常亮/呼吸/关闭」
> （G24 上不显示该项）。
> **本工具的做法**：仍按 `.ict` 格式保存/读回每档颜色（导出兼容、界面用它区分档位与滑杆配色），
> DPI 页已去掉改色入口，并明确标注颜色不可改。
>
> 接收器指示灯同样**不支持自定义颜色/亮度**：命令第 2 字节只接受模式值 0/1/2，
> 具体配色由接收器固件按回报率或电量自行决定。UI 上的颜色对照是说明，不是可选项。

> **官方说明书的定案（2026-11-16 补充）**：G24 系列用户手册 §5.4 写明 8K 接收器灯效 =
> 连接状态 + 回报率，颜色表 **红 125 / 蓝 250 / 黄 500 / 橙 1000 / 紫 2000 / 绿 4000 / 白 8000**；
> 电量低于 33% 时改为 绿 100% → 黄 66% → 橙 33% → 红 0%。本体那颗 key indicator light 只负责
> 配对闪烁、充电红灯与低电量闪红。**全文没有任何「按 DPI 档位显示颜色」或「颜色可配置」的描述。**
>
> 由此也澄清了 2026-11-16 的一次误判：用户看到「切配置后灯色变了」，实际是切换配置顺带改了回报率
> （配置 1 = 2000Hz → 紫、配置 2 = 1000Hz → 橙），并非颜色设置生效。本工具已把 DPI 页的改色入口
> 降级为纯界面标识，详见 [led-behavior.md](led-behavior.md)。

### 3.9 Profile 切换 `[6, 9, index, 0,0,0,0,0]`

> **实机验证（2026-11-15，G24 有线 PAW3950）**：把 `[6,9,idx]` 依次写到 0~5 再逐项回读，
> 得到的 DPI 档位/灯色、按键映射、回报率、节能时间**完全一致**，只有 `0x86,9` 回读的序号跟着变
> （写 0..5 都能回读成功）。结论：**硬件只有 1 份配置**，matrix 9 写入的只是当前配置的索引标记。
>
> 官方桌面驱动（v1.3.7 `Language/ch.xml` 的 `str_profile1..5`、`str_changle_profile`）提供的
> **5 个「配置」是 PC 端预设**，切换时把整套配置「灌入」鼠标。本工具按同样语义实现
> （`src/renderer/app.js` 的 `switchProfile`：保存当前槽 → 载入目标槽 → 整套 apply + setProfile）。
>
> 设备主动上报里也有配置序号（`parseStatusPush` 的 `b2` 高 2 位），用于跟随鼠标上的配置切换键；
> 2 位只能表达 0~3，第 5 个配置无法从推送里区分，属于固件限制。

## 4. 读取命令（byte 0 = 命令码，回显在数据区 byte 0）

**写命令 `0x01`~`0x08` 对应读命令 `0x81`~`0x88`**（Caldis G24 有线实机验证，54 条参数扫描 51 条符合），
另有 `0x89` 状态 / `0x8E` 配对 / `0x8F` 型号信息三条独立读命令。
（历史文档用十进制 131~143 即十六进制 0x83~0x8F，两者一致。）

| 命令码 | 用途 | 返回关键字段（已剥离 reportId） | 实机验证 |
|---|---|---|---|
| `0x81` | 回报率 | buf[1] = 回报率索引 | 125~1000Hz 写后回读成功；**2000/4000/8000 被硬件钳制为 1000**（有线/非 8K 接收器） |
| `0x82,slot` | 单档 DPI | buf[2..3] = 硬件值（16 位小端），DPI = (raw+1)×50 | 50/1600/32000 成功 |
| `0x83` | 档数及当前档 | buf[1]=count, buf[2]=active | 六档回读成功（原版网页驱动 `readDpiInfo` 取错字节 3/2，实际在 1/2） |
| `0x84,sub` | 传感器参数 | buf[2] = 值 | LOD/波纹/直线/MotionSync/传感器模式全部回读成功 |
| `0x85,sub` | 消抖/连发/休眠 | sub1: buf[2]；sub2: buf[2]=loops, buf[3]=interval；sub3: buf[2..3] 16 位秒 | 消抖 0/8/30ms、连发 loops 0~3 成功；无线休眠未实测 |
| `0x86,matrix` | 按键映射 | 32 位键码 = buf[5]<<24\|buf[4]<<16\|buf[3]<<8\|buf[2]；**matrix=9 时 buf[2] 是当前配置序号** | 11 种鼠标功能、普通键、Ctrl+A、播放/暂停、静音回读成功 |
| `0x87` | 宏内容 | **该固件返回 8 个 0xFF（宏不可回读）** | 发送成功 ≠ 回读成功 |
| `0x88` | 接收器 LED | buf[1] | 8K 接收器功能，未实测 |
| `0x89` | 完整状态 | buf[1]=电量 0-100（>128 表充电中，减 128）/档位/回报率索引/当前 DPI | 读取成功；原版电量向下取整到十位 |

> **电量主通道是设备主动上报（Input Report）**：电量/回报率/DPI/板载配置变化时设备推送状态包，
> 布局 `b0=电量|充电位128, b1=回报率索引|DPI索引<<4, b2=配置序号<<6`（见 `parseStatusPush`）。
> 官方 UI 的「电量同步中」即等待推送；0x89 轮询只作补充。
> 注意：Feature Report 9 数据区固定 8 字节（HID 描述符确认），不可按 64 字节读所谓「电压字段」
> ——Windows `HidD_GetFeature` 要求缓冲区等于报告长度，超长读取会失败或返回填充数据。
| `0x8E,1` | 配对状态 | buf[6]==1 表示在线 | 原版配对按钮为空函数，无可用配对实现 |
| `0x8F` | 型号信息 | buf[1]=1 标志；buf[2]=型号码；buf[3]=接收器类型（**2=8K**）；传感器字节：**有线 buf[4] / 无线 buf[5]**，**241=PAW3950**，否则 PAW3395 | G24、PAW3950 识别成功 |

型号码：1=Ghero, 2=G23, 3=G24, 6=G29, 8/14=G23V2, 9=FM23（`protocol.js MODEL_TABLE`）。

> 读取流程：发送 `[cmd, flag...]` → sleep 25~50ms → `getFeatureReport(9)` → 校验返回 byte 0 == cmd。
> Feature Report 数据区就是 **8 字节**（HID 描述符确认，hidapi 总长传 9 = 1 reportId + 8 数据），不要假设 32 字节。

## 5. 键码编码（32 位，`kf_hw` 返回值）

### 5.1 鼠标键
| 功能 | 键码 |
|---|---|
| 左键 | `0x00F00001` |
| 右键 | `0x00F10001` |
| 中键 | `0x00F20001` |
| 前进 | `0x00F40001` |
| 后退 | `0x00F30001` |
| DPI 循环 | `0x00030007` |
| DPI+ | `0x00010007` |
| DPI- | `0x00020007` |
| Profile 切换 | `61706` (0xF10A) |
| 火力键 | `0x0218F00A` |
| 禁用 | `0` |

### 5.2 键盘键
- 无修饰：`(minor & 0xFF) << 8 | 0x80`（minor 为 HID 键码，见 HID 键码表）
- 有修饰：`(minor & 0xFF) << 16 | (modifier & 0xFF) << 8`
- 修饰键位掩码：CtrlL=1, ShiftL=2, AltL=4, WinL=8, CtrlR=16, ShiftR=32, AltR=64, WinR=128

### 5.3 多媒体键（格式 `0xXXYY0003`）
PLAYER=`0x01830003`, PLAYPAUSE=`0x00CD0003`, STOP=`0x00B70003`,
PREVIOUS=`0x00B60003`, NEXT=`0x00B50003`, VOLINC=`0x00E90003`, VOLDEC=`0x00EA0003`,
MUTE=`0x00E20003`, EMAIL=`0x018A0003`, CAL=`0x01920003`, EXPLORER=`0x01940003`,
HOME=`0x02230003`, REFRESH=`0x02270003`, FORWARD=`0x02250003`, BACK=`0x02240003`,
SEARCH=`0x02210003`

### 5.4 宏
`index << 16 | 9`（index 为宏槽位）

## 6. 宏数据格式（320 字节）

```
[0]     = 槽位 bufferID
[1]     = 循环类型：0=按住循环, 1=任意键停止, 2=循环N次
[2..3]  = 循环次数（16 位）
[4..]   = 宏项（每项 4 字节）：[press?0:128 | 1, HID键码, 延迟低, 延迟高]
[288..293] = "Macro"+编号 标记
[304..307] = size（32 位，=(项数+1)*4+128）
[312..315] = uid（32 位）
[316..317] = 项数*2
[318]     = 项数
```

## 7. DPI 映射

- 硬件值 = `(实际DPI - 50) / 50`（线性，步进 50）
- PAW3395：50 ~ 32000（硬件值 0 ~ 639）
- PAW3950：50 ~ 45000（硬件值 0 ~ 899）

## 8. 应用流程（apply）

按序发送（每步之间 sleep ~200ms）：
1. 按键映射（火力键、宏、普通键）
2. DPI 档位值（setResolution，XY 分离时分两次）
3. DPI 档位切换（setDif）
4. 轮询率（setRte）
5. 传感器模式（setSM）
6. LOD（setLD）
7. 波纹/角度吸附/运动同步（setRi/setFix/setMt）
8. 接收器 LED（setReceiverLED）
9. 去抖（setDce）
10. 睡眠时间（setSep）
11. Profile 切换（setProfileIndex）
